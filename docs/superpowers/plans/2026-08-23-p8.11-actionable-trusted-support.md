# P8.11 Actionable Trusted Support Implementation Plan
> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make optional setup persist an authenticated user's trusted contact safely and turn the result-page trusted-support panel into a genuinely actionable, consent-led experience.

**Architecture:** The existing email OTP session remains the sole authentication mechanism. Setup data stays in DynamoDB; trusted contact email and phone are encrypted with AES-256-GCM before persistence, with deterministic hashes retained for lookup/integrity. The client receives decrypted contact details only through the authenticated setup endpoint. Result-page actions are derived locally from that authenticated setup snapshot.

**Tech Stack:** Next.js App Router, TypeScript, React, DynamoDB, Amazon SES, Node.js crypto, Node test runner.

**Spec:** `docs/superpowers/specs/2026-08-22-p8.11-actionable-trusted-support-design.md`

## Global Constraints

- Optional setup must never block a safety check.
- No automatic contact, sharing, or notification of trusted people.
- Do not log direct contact details or include them in safety-event data.
- Preserve legacy hash-only trusted-contact records without exposing invented contact data.
- Remove the unused support-code experience from active UI and API contracts.
