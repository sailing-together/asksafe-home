# P7.2 Guided Clarification Interaction Design

Date: 2026-06-23

Owner: Cynthia Zhang

## Goal

Use the P7.1 `SafetyResult.clarification` signal to improve Step 2 of the
AskSafe check flow.

When a user gives thin but risky context, AskSafe should ask one purposeful
follow-up question before showing the final result. This should make the
interaction feel more helpful and less repetitive without turning AskSafe into a
generic chatbot.

This reduces uncertainty and decision pressure for seniors by helping them
check the one missing detail that matters before they act.

## Product Principle

AskSafe should ask one helpful clarification question only when it reduces
uncertainty or decision pressure.

If the situation already contains a hard-stop signal, AskSafe should move
directly toward the safer next step. It should not slow the user down with extra
conversation when the safe advice is already clear.

## Current Context

P7.1 added a deterministic clarification signal to `SafetyResult`:

```ts
clarification?: {
  needed: true
  question: string
  reason: string
}
```

The current Step 2 interaction in `components/situation-input.tsx` already feels
chat-like, but its assistant replies are generated locally in
`buildAssistantReply()`. Those replies can be repetitive, especially when the
user adds similar details more than once.

The result page can now show a "Before you decide" clarification card, but the
user should ideally see the clarification while still describing the situation,
before moving to the result screen.

## Non-Goals

- Do not build an open-ended chatbot.
- Do not let Bedrock decide whether clarification is needed.
- Do not ask multiple follow-up questions in one check.
- Do not request bank account numbers, passwords, one-time codes, identity
  documents, full card numbers, or private payment details.
- Do not delay hard-stop guidance for one-time codes, app installs, screen
  sharing, personal details, gift cards, crypto, secrecy, threats, or coercion.
- Do not redesign the whole home page, result page, support setup, or official
  help area in this slice.

## Design Options Considered

### Option A: Keep Current Step 2 And Only Show Clarification On Result

This is the lowest-risk implementation because P7.1 already supports it.
However, the user still experiences a weak Step 2 interaction before seeing the
better clarification card.

This does not fully address the product problem.

### Option B: One Purposeful Follow-Up In Step 2

AskSafe runs a lightweight deterministic check after the first user detail. If
the result includes `clarification`, Step 2 shows that single question as an
assistant bubble and lets the user answer or continue to the safer next step.

This is the recommended approach because it uses the new rule-owned signal,
keeps the flow controlled, and avoids chatbot sprawl.

### Option C: Bedrock-Generated Follow-Up Conversation

Bedrock could generate more natural follow-up questions. This may improve tone
eventually, but it introduces safety risk because the model may ask for
sensitive details or keep the user talking when they need to stop.

This should not be used for P7.2.

## Recommended Approach

Implement Option B.

Step 2 should use the same deterministic analysis path already used by the
result flow, but only to decide whether a single clarification question is
needed. The user remains in control:

- they can answer the clarification;
- they can choose action chips;
- they can skip straight to the safer next step once they have entered at least
  one detail;
- AskSafe does not keep asking more questions after the first clarification.

## User Flow

### 1. User Selects Situation Type

The user chooses a category such as phone call, text or email, money or
payments, video call or online chat, or something else.

### 2. AskSafe Starts Step 2

AskSafe shows the current category-specific prompt and action chips.

Example for video:

```text
What happened on the video call or chat? Who were they, and what did they ask you to do?
```

### 3. User Sends First Detail

Example:

```text
my daughter asked me for money
```

AskSafe evaluates the current detail and selected chips using deterministic
safety logic.

### 4. Clarification Is Needed

If the deterministic result includes `clarification`, AskSafe shows one
assistant bubble:

```text
Before you decide, check one thing: how did they contact you, and how do they want the money sent?
```

Under the bubble, AskSafe should show a short helper line:

```text
You can answer this, or choose the safer next step now.
```

This keeps the user from feeling trapped in a conversation.

### 5. User Answers Or Continues

If the user answers, the answer is appended to the details. AskSafe may respond
with a short acknowledgement, not another question:

```text
Thank you. I have enough to show the safer next step.
```

If the user does not answer, they can still choose the safer next step because
they have already entered one detail.

### 6. Result Is Shown

The final analyze call uses the combined user details and selected action chips.
The result may still include the clarification card, but it should not feel like
the only place the user learns what to check.

## When Step 2 Should Ask Clarification

Ask clarification when all of these are true:

- the user has entered at least one detail;
- the result includes `clarification.needed`;
- the clarification has not already been asked in this check;
- there is no hard-stop action selected or detected.

Examples:

- "my daughter asks me for money"
- "someone asked me to pay"
- "a caller says I owe money" with `pay` selected

## When Step 2 Should Not Ask Clarification

Do not ask clarification when the user selected or described:

- share a code;
- install an app;
- share my screen;
- give personal details;
- passwords, PINs, one-time codes, or verification codes;
- remote access tools;
- gift cards, crypto, or unusual transfers;
- secrecy, threats, or immediate coercion.

For these cases, Step 2 should not add a conversational delay. It may show a
short assistant acknowledgement such as:

```text
I have enough to show the safer next step.
```

## Interaction Rules

1. Ask at most one clarification question per check.
2. Never ask for sensitive information.
3. Keep the question as one sentence.
4. Keep the assistant reply under two short lines on mobile when possible.
5. Preserve the "Show me the safer next step" action once the user has entered
   one detail.
6. Do not remove action chips; they help users communicate without typing much.
7. Do not hide the text or voice input after asking clarification.
8. If voice recognition adds messy text, the user can still continue. Do not
   require perfect wording.

## Suggested Copy

Clarification bubble:

```text
Before you decide, check one thing: how did they contact you, and how do they want the money sent?
```

Helper line:

```text
You can answer this, or choose the safer next step now.
```

Acknowledgement after answer:

```text
Thank you. I have enough to show the safer next step.
```

Hard-stop acknowledgement:

```text
I have enough to show the safer next step.
```

Avoid:

```text
Please provide the exact account number, full payment details, and personal information.
```

## State Model

Step 2 can remain local component state. It does not need backend persistence in
this slice.

Recommended local state:

```ts
type ClarificationState =
  | { status: "not-needed" }
  | { status: "available"; question: string; reason: string }
  | { status: "asked"; question: string; reason: string }
  | { status: "answered"; question: string; reason: string }
```

The component should also track:

- `details`: all user messages submitted in Step 2;
- `requests`: selected action chips;
- `hasAskedClarification`: whether the single clarification has already been
  shown.

## Data Flow

1. User submits first Step 2 detail.
2. Step 2 runs deterministic local analysis using the current message,
   category, and selected request chips.
3. If `result.clarification` exists and hard-stop rules do not apply, Step 2
   shows the clarification bubble.
4. If the user answers, Step 2 appends the answer to `details`.
5. Final submit calls the existing `onSubmit(message, requests)` contract.
6. The existing API and result flow remain unchanged.

This keeps P7.2 compatible with the existing result flow and safety event
persistence.

## Example Conversations

### Thin Family Money Request

User:

```text
my daughter asked me for money
```

AskSafe:

```text
Before you decide, check one thing: how did they contact you, and how do they want the money sent?
```

User:

```text
video call, she said she needs 2000 AUD
```

AskSafe:

```text
Thank you. I have enough to show the safer next step.
```

### Vague Payment Request

User:

```text
someone asked me to pay
```

AskSafe:

```text
Before you decide, check one thing: who is asking, and how do they want you to pay?
```

### Hard-Stop Code Request

User:

```text
they asked for my one-time code
```

AskSafe:

```text
I have enough to show the safer next step.
```

No extra clarification question should appear.

## Mobile UX Notes

- The clarification bubble should use the same assistant bubble style as current
  Step 2 messages.
- Keep spacing compact so the input composer and action chips remain reachable.
- Do not add another large card inside the Step 2 conversation.
- The safer-next-step button should remain prominent below the conversation
  once the user has entered one detail.
- On small screens, avoid stacking long explanatory text under the bubble.

## Accessibility Notes

- New clarification messages should remain inside the existing
  `aria-live="polite"` conversation region.
- The clarification should be plain text, not only visual styling.
- Do not rely on color alone to show that a clarification was asked.
- Keyboard users should still be able to move from message input to action chips
  to safer-next-step button in a predictable order.
- Voice users should be able to answer the clarification using the same voice
  input control.

## Test Scenarios

Add tests or manual QA checks for these scenarios:

1. Thin family money request asks one clarification question.
2. Answering the clarification does not create a second clarification question.
3. Vague payment request asks the payment clarification question.
4. Code request skips clarification and allows safer-next-step flow.
5. Install-app request skips clarification and allows safer-next-step flow.
6. Screen-share request skips clarification and allows safer-next-step flow.
7. Low-risk appointment reminder does not ask clarification.
8. Voice-entered text can trigger the same clarification behavior as typed text.

## Acceptance Criteria

- Step 2 uses the P7.1 clarification signal for thin risky context.
- AskSafe asks no more than one clarification question per check.
- Hard-stop cases do not receive an extra clarification question.
- The existing `onSubmit(message, requests)` contract is preserved.
- The result page and backend analyze route continue to work without API shape
  changes beyond the already-added P7.1 `clarification` field.
- Mobile layout remains readable and does not add excessive vertical space.
- The interaction still feels like a guided safety workflow, not a generic
  chatbot.

## Rollout

P7.2 should be implemented as a focused frontend interaction change after this
spec is reviewed.

The next implementation plan should keep commits small:

1. add focused tests for clarification interaction behavior;
2. refactor Step 2 local reply logic to use `analyze()` or the P7.1
   clarification signal;
3. preserve hard-stop behavior;
4. update manual QA notes.

Bedrock-generated follow-up questions should remain out of scope until the
rule-owned interaction is proven useful.
