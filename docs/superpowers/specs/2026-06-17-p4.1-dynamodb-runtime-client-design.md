# P4.1 DynamoDB Runtime Client Design

## Goal

Add a small server-side persistence foundation for AskSafe Home so later product
flows can write safety events, feedback, and support events to DynamoDB without
making the user experience depend on AWS availability.

This reduces uncertainty for seniors by making future safety checks recordable
and auditable, while keeping the immediate guidance flow calm and resilient if
the backend is unavailable.

## Scope

P4.1 adds backend runtime building blocks only.

In scope:

- server-only DynamoDB client construction
- runtime environment validation
- typed table-name configuration
- persistence helpers for safety events, feedback, and support events
- graceful failure behavior when AWS configuration or writes fail
- unit tests for config validation and persistence payload shaping

Out of scope:

- changing the existing UI flow
- adding authentication
- adding Bedrock
- storing raw sensitive user messages by default
- wiring Vercel environment variables in this PR
- importing or migrating existing data

## Runtime Environment

The runtime should read these environment variables:

- `AWS_REGION`
- `ASKSAFE_EVENTS_TABLE`
- `ASKSAFE_FEEDBACK_TABLE`
- `ASKSAFE_SUPPORT_EVENTS_TABLE`

The helper may also define config support for later tables:

- `ASKSAFE_USERS_TABLE`
- `ASKSAFE_HOUSEHOLDS_TABLE`

Missing required variables should not crash client-side rendering. Server-side
persistence helpers should return a structured skipped or failed result so the
caller can continue showing the safety result.

## Data Minimisation

P4.1 should not store the raw message by default.

Safety event payloads may include:

- generated event id
- created timestamp
- category
- selected request types
- risk level
- risk signal ids and labels
- scam type ids
- source ids
- optional anonymous session id

Safety event payloads should not include:

- raw message text
- passwords
- one-time codes
- card numbers
- full identity details

Future work may add explicit user-controlled sharing or redacted summaries, but
that is not part of P4.1.

## Proposed Modules

Add a focused server-side runtime layer under `lib/server/`:

- `lib/server/aws-env.ts`
  - validates runtime env values
  - returns typed table names
  - exposes a safe validation result

- `lib/server/dynamodb.ts`
  - constructs a DynamoDB DocumentClient
  - stays server-only

- `lib/server/persistence.ts`
  - exports `saveSafetyEvent`
  - exports `saveFeedbackEvent`
  - exports `saveSupportEvent`
  - returns `{ ok: true }`, `{ ok: false }`, or `{ skipped: true }`

The helpers should accept plain typed objects so UI and API routes can call them
later without knowing DynamoDB details.

## Error Handling

Persistence must be best-effort at this stage.

If env variables are missing:

- return a skipped result
- include a non-sensitive reason for logs or tests
- do not throw into the user flow

If DynamoDB write fails:

- return a failed result
- avoid exposing AWS error details to the browser
- keep enough internal detail for server logs in a future API route

This matches the product requirement that an older adult should still receive
their safer next step even if persistence fails.

## Testing

Add focused tests that run without real AWS access:

- env validation succeeds with required variables
- env validation reports missing variables
- safety event payload excludes raw message text
- helper returns skipped when config is missing

Tests should not call AWS. If the AWS SDK client is introduced, write tests
around payload shaping and config behavior rather than live network calls.

## Follow-Up Work

P4.2 should wire the helper to a server route or server action for safety check
events.

Later PRs can add:

- feedback persistence from the result page
- support event persistence
- user setup persistence after authentication is real
- Bedrock explanation assist after deterministic safety rules remain stable
