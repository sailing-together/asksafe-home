# P7.1 Guided Clarification Design

Date: 2026-06-20

## Goal

AskSafe should avoid sounding like it has already decided the whole situation
when the user has only shared a thin description such as "my daughter asks me
for money".

P7.1 adds a small, rule-owned clarification signal to the safety result so the
product can say what still needs checking before the user acts.

This reduces uncertainty and decision pressure for seniors by giving one clear
question to verify, without making them complete a long form or trust a generic
chatbot.

## Non-Goals

- Do not rebuild the Step 2 chat UI in this slice.
- Do not let Bedrock decide whether clarification is needed.
- Do not ask for bank account numbers, passwords, one-time codes, identity
  documents, or private payment details.
- Do not delay urgent hard-stop advice for high-risk actions such as sharing a
  code, installing an app, sharing a screen, gift cards, crypto, or secrecy.

## Current Context

`lib/safety-rules.ts` already produces a `followUpQuestion`, but `lib/analyze.ts`
does not expose it through `SafetyResult`. The Step 2 chat component currently
has its own hand-written follow-up replies, which can feel repetitive and less
grounded in the actual safety rules.

P7.1 should reuse the existing rule assessment instead of creating a separate
clarification engine.

## Proposed Shape

Add an optional `clarification` object to `SafetyResult`:

```ts
type Clarification = {
  needed: boolean
  question: string
  reason: string
}
```

The result can omit `clarification`, or include `needed: false`, when no useful
follow-up is needed. The first implementation should prefer including it only
when a follow-up would materially help.

## Alternatives To Re-Evaluate Later

The team considered three possible implementation levels:

1. Minimal clarification signal: expose rule-owned `followUpQuestion` /
   `clarification` through `SafetyResult`. This is the recommended P7.1 slice
   because it is small, testable, and keeps risk decisions deterministic.
2. Medium Step 2 chat rewrite: update the guided input conversation to use
   clarification slots and ask better follow-up questions before showing the
   result. This is a likely P7.2 candidate after the data contract is stable.
3. Bedrock-generated follow-up questions: let Bedrock help phrase questions or
   suggest one follow-up. This should be re-evaluated only after the rule-owned
   clarification path is working, because Bedrock should not decide risk level
   or whether a clarification is needed.

## When Clarification Is Needed

Clarification should be included when:

- the result is risky but context is thin;
- a family or trusted-person money request is detected;
- the user selected a risky request type but did not explain who contacted them
  or how they are supposed to act;
- the next safe action depends on independent verification.

Example:

Input:

```text
my daughter asks me for money
```

Clarification:

```text
Before you decide, check one thing: did you contact her using a number or account you already trust?
```

## When Clarification Should Not Slow The Flow

Clarification should not weaken or delay hard-stop safety guidance when the
input includes high-risk actions such as:

- sharing a one-time code, password, or PIN;
- installing an app;
- sharing a screen;
- sending gift cards, crypto, or unusual transfers;
- keeping the request secret;
- immediate threat or coercion.

These cases can still include verification guidance in the result, but the
primary message remains: stop, do not do the requested action yet, and verify
through a trusted channel.

## Wording Principles

- Ask one question, not a list.
- Ask about safe context, not sensitive details.
- Prefer "check" and "verify" over "prove" or "detect".
- Preserve dignity: acknowledge that the request could be real, but payment or
  sharing should wait until verified.

Good example:

```text
Before you decide, check one thing: can you reach them another way you already trust?
```

Avoid:

```text
Enter their bank account, phone number, exact address, and all payment details.
```

## Architecture

`assessSafetyInput()` remains the source of rule-owned clarification wording.
`analyze()` maps that assessment into `SafetyResult.clarification`.

Bedrock receives the clarification context later only as bounded, redacted
metadata for wording polish. It does not decide the risk level or whether
clarification is needed.

## Testing

Add unit tests for:

- family money request returns a clarification question;
- vague payment request returns a clarification question;
- code, install, and screen-share requests still return high-risk hard-stop
  guidance;
- low-risk input does not produce unnecessary clarification;
- API response remains backward compatible for existing result rendering.

## Rollout

P7.1 only adds the data capability. P7.2 can update the Step 2 conversation UI
to use `clarification.question` so the assistant stops repeating generic
responses and asks the most useful next question.
