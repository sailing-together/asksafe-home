# P8.11 Actionable Trusted Support Design

## Status

Proposed design for review. This document deliberately defines the next production implementation before changing product code.

## Goal

Make optional setup useful after it has been saved: a signed-in senior should return directly to their existing setup, their saved trusted contact should be available as a user-controlled call or email action from a safety result, and the product must not present a short support code as though it grants access.

This supports the AskSafe Founder Rule by reducing uncertainty and decision pressure without making setup, sign-in, or family involvement mandatory.

## Product Decisions

### Core Safety Check Remains Anonymous

The safety check remains fully usable without sign-in. `My setup` is optional continuity for a user who chooses it; it is not an account wall before urgent safety guidance.

### Existing and New Users Have Different Post-OTP States

After a correct one-time email code:

- an existing user with a saved setup sees `My AskSafe setup` directly;
- a new user sees `Set up AskSafe`;
- neither path briefly renders the setup form before the correct state is known.

The verification response must set the session cookie and return an authenticated setup snapshot in the same response. The client uses that snapshot immediately rather than waiting for a second `/api/setup/me` request.

### Saved Trusted Contacts Are Actionable, but Never Automatic

On a result page, AskSafe shows a user-chosen contact action only when a saved contact method exists:

| Saved data | Result action |
| --- | --- |
| name and phone | `Call <name>` linking to `tel:` |
| name and email | `Email <name>` linking to `mailto:` |
| name, phone, and email | `Call <name>` as primary and `Email <name>` as secondary |
| name but no recoverable contact method | `Add <name>'s contact details` |
| no trusted person | `Add someone I trust` |

The existing copy-summary action can remain as an explicit user action. P8.11 does not send a message, notify a relative, create a relative dashboard, or share a safety result automatically.

### Retire the Visible Support Code

`SAFE-xxxx` is not an authentication, consent, or secure pairing mechanism. P8.11 removes the visible `Create support code`, copy-code, and support-code display UI. Existing DynamoDB `supportCode` values remain read-compatible and are neither deleted nor used to authorize access.

Explicit recipient consent, invitation, and account pairing are a separate future P8.12 capability.

## Data and Privacy Design

### Owner Data

The existing user email continues to be represented by its deterministic hash for user lookup. The raw sign-in email is used transiently to deliver the one-time code and is not returned as a stored user profile field.

### Trusted Contact Data

Hashes alone cannot power a user-selected call or email action. When the owner chooses to save a trusted phone number or email address, P8.11 stores:

- `trustedEmailHash` and `trustedPhoneHash` for deterministic lookup and integrity use;
- `trustedEmailEncrypted` and/or `trustedPhoneEncrypted` for owner-only recovery; and
- `trustedContactEncryptionVersion: 1`.

Encrypted values use server-only AES-256-GCM with:

- a 32-byte base64 secret in `ASKSAFE_TRUSTED_CONTACT_ENCRYPTION_SECRET`;
- a newly random 96-bit IV for every encryption operation;
- an authentication tag; and
- fixed additional authenticated data `asksafe-home:trusted-contact:v1`.

The stored representation contains version, IV, ciphertext, and tag encoded as base64url. It must never contain a raw contact value. The encryption helper must reject malformed payloads, a missing or invalid secret, and failed authentication tags.

Raw trusted contact values are decrypted only on the server for the signed-in owner's `GET /api/setup/me` response. They must not be written to logs, analytics, safety events, feedback events, or support event payloads.

### Legacy Records

Existing household records may have a name and hash but no encrypted contact method. They remain valid records. The UI must not imply that AskSafe can call or email them; it instead offers the owner `Add <name>'s contact details`. No background migration, destructive rewrite, or unprompted deletion occurs.

### Server Failure Boundary

If a save request contains trusted contact email or phone and the encryption secret is unavailable or invalid, saving fails closed with a clear, non-sensitive error. Anonymous safety guidance continues to work.

## API Contract

### Verify Code

`POST /api/setup/verify-code` continues to accept `{ email, code }` and set an HTTP-only, Secure, SameSite=Lax session cookie. Its successful JSON response becomes:

```json
{
  "ok": true,
  "signedIn": true,
  "signedInEmail": "person@example.com",
  "setup": {
    "yourName": "Margaret",
    "email": "",
    "phone": "",
    "usingFor": "self",
    "trustedName": "Sarah",
    "relationship": "Daughter",
    "trustedEmail": "sarah@example.com",
    "trustedPhone": "+61400111222"
  }
}
```

`setup` is `null` for a newly authenticated user with no profile. The response must not include OTP values, encryption material, hashes, or legacy `supportCode` values.

### Load and Save Setup

`GET /api/setup/me` returns the same owner-authorized setup shape. `PUT /api/setup/me` accepts owner-entered trusted contact details and writes their hashes plus encrypted values. The public client type removes `code`.

The session owner can read only the household record whose `ownerUserId` matches their signed session. No unauthenticated or trusted-contact endpoint is added.

## UX States and Copy

### Setup Dialog

The dialog gains a transient `resolving` state after code submission. It keeps the code panel visible with an in-progress label while the server response is being applied; it never switches to the form speculatively.

The setup form retains its current optional language and adds no new account requirement. When a saved trusted contact has methods, edit mode pre-fills the owner-visible phone and email fields. Legacy hash-only contacts show an explanation that contact details need to be added again before AskSafe can make them available as a direct action.

### Result Support Panel

Use direct action labels rather than a generic setup prompt whenever an action is available. The panel always states that sharing or contacting someone is the user's choice. A call or email link opens only after the user presses it.

## Non-Goals

P8.11 does not implement:

- SMS or phone OTP;
- magic-link sign-in;
- trusted-contact invitations, recipient authentication, or a family portal;
- automatic result sharing, notification, monitoring, or escalation;
- short-code pairing or authorization;
- changes to the deterministic safety rules, Bedrock workflow, or anonymous safety-check access.

## Infrastructure and Configuration

DynamoDB remains schemaless for these additive household attributes. Existing runtime DynamoDB read/write permissions are sufficient; no new table or index is needed.

Configure `ASKSAFE_TRUSTED_CONTACT_ENCRYPTION_SECRET` as a Vercel environment secret for Production and Preview. Generate it from 32 cryptographically random bytes encoded as base64. It must not appear in Terraform state, source control, client JavaScript, logs, or test fixtures.

No SES or CloudFormation change is required by P8.11. Email OTP delivery stays on the existing SES production configuration.

## Acceptance Criteria

1. A signed-in user opening a new same-browser tab is restored by their HTTP-only session and sees their saved setup without requesting a new code.
2. An existing user who verifies an OTP transitions directly from code entry to setup summary, without a visible setup-form flash.
3. A newly authenticated user transitions directly from code entry to setup form.
4. Saving trusted phone or email persists an encrypted value, not plaintext, while preserving the appropriate hash.
5. A signed-in owner can edit and recover their saved trusted contact methods; another session cannot load them.
6. Result pages expose the call/email/add-details action matrix defined above, with no automatic contacting or sharing.
7. No visible support-code creation, display, or copy action remains.
8. Existing hash-only contacts remain intact and are guided to add contact details instead of producing a broken action.
9. Tests cover encryption/decryption, random IV behavior, tamper failure, missing-secret failure, owner-only hydration, atomic OTP snapshot behavior, dialog state selection, legacy contact behavior, and the result action matrix.
10. Anonymous safety checks still work when no session or setup exists.

## Verification Plan

Run focused unit/component tests for setup authentication, setup routes, client setup calls, the trusted support dialog, the result card, and the new encryption helper. Then run lint and production build.

Perform a browser walkthrough for:

1. anonymous safety check with no sign-in;
2. new email OTP user -> setup form -> save trusted name plus phone/email;
3. existing email OTP user -> summary with no setup-form flash;
4. new browser tab -> restored optional setup;
5. result page -> `Call <name>` / `Email <name>` actions;
6. legacy contact record -> add-details action; and
7. sign-out -> an unauthenticated setup flow.

## Follow-on: P8.12 Trusted Contact Consent and Pairing

Before any trusted person can receive content, P8.12 must introduce an explicit consent and pairing design: an owner-created invitation, a recipient acceptance flow, least-privilege access, revocation, audit events, data retention rules, and a clear explanation of exactly what will be shared. A support code alone is explicitly insufficient.
