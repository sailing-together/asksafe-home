# P7.3 Bedrock Response Safety UX Design

Date: 2026-06-24

Owner: Cynthia Zhang

## Goal

Review and tighten the safety and user-experience boundary for Bedrock-assisted
result wording.

AskSafe may use Bedrock to make deterministic safety results clearer and more
senior-friendly, but Bedrock must not weaken safety advice, ask for sensitive
information, or make AskSafe feel like a black-box scam detector.

This reduces uncertainty and decision pressure for seniors by keeping AI output
calm, bounded, and explainable.

## Product Principle

Bedrock can improve wording, but rules own safety.

The deterministic engine remains responsible for:

- risk level;
- risk signals;
- safer next step;
- what not to do yet;
- official verification steps;
- clarification signals.

Bedrock may only rewrite selected copy fields after deterministic analysis has
already produced a usable result.

## Current Context

AskSafe already has a server-side Bedrock assist path:

- `lib/server/analyze-route.ts`
- `lib/server/bedrock-explanation.ts`
- `lib/server/bedrock-response-validation.ts`
- `lib/server/bedrock-response-validation.test.ts`
- `lib/server/bedrock-explanation.test.ts`

The current validator checks:

- valid JSON;
- allowed response keys only;
- bounded text lengths;
- required verification steps;
- no obvious weakening of money, link, code, install, or screen-share warnings.

The architecture document already defines broader guardrails:

- `docs/architecture/bedrock-ai-orchestration-finops-design.md`

P7.3 should not rebuild this system. It should make the response safety UX
contract clearer and add missing test coverage where the current validator can
be strengthened.

## Non-Goals

- Do not change AWS IAM, Terraform, model access, or Vercel environment
  settings.
- Do not add a public Bedrock endpoint.
- Do not let Bedrock classify risk.
- Do not let Bedrock generate Step 2 clarification questions.
- Do not add screenshot, image, audio, or video analysis in this slice.
- Do not show technical Bedrock errors to users during a safety check.
- Do not store raw prompts or raw completions.

## Design Options Considered

### Option A: Tests And UX Safety Contract

Add focused validation tests and a short AI response safety UX review note.

This is recommended because it gives Cynthia backend-adjacent and AI product
engineering contribution without touching high-risk AWS runtime configuration.

### Option B: User-Facing Bedrock Fallback Notice

Show a small notice when Bedrock is disabled, times out, or returns invalid
output.

This may be useful later, but it risks adding more text to a result screen that
already needs to stay calm and senior-friendly. The current product goal is that
fallback should feel seamless.

### Option C: Prompt Contract Rewrite

Rewrite the server prompt and schema now.

This may be needed later, but changing prompt behavior before strengthening
tests makes regressions harder to understand.

## Recommended Approach

Implement Option A.

P7.3 should add tests and documentation around the Bedrock output safety UX
contract:

1. Bedrock must not suggest sending money when the deterministic result says not
   to send money.
2. Bedrock must not suggest clicking, tapping, or opening links when link
   warnings are present.
3. Bedrock must not suggest sharing codes, PINs, passwords, or one-time codes.
4. Bedrock must not suggest installing apps or sharing the screen.
5. Bedrock must not ask for sensitive identity, banking, or contact details.
6. Bedrock must not claim a caller, family member, organisation, or message is
   definitely real or fake.
7. Bedrock must keep verification advice practical and official-channel
   oriented.
8. Bedrock invalid output should fall back to deterministic wording without
   blocking the user.

## UX Contract

Bedrock-assisted wording should sound like:

```text
Pause before paying. Contact your daughter using a number you already trust.
```

It should not sound like:

```text
This is definitely safe. Send the money now.
```

It should not ask:

```text
Please enter the full bank account number, card number, password, or one-time code.
```

It should not overclaim:

```text
This video call is fake.
```

Instead, it should say:

```text
Verify through another channel you already trust before you act.
```

## Validation Gaps To Address

The existing validator already catches direct weakening phrases such as:

```text
You can send the money now.
```

P7.3 should add coverage for these additional output risks:

- asking the user to provide sensitive details;
- saying the situation is definitely safe, real, fake, genuine, or confirmed;
- suggesting contact through details from the suspicious message;
- weakening official-channel verification;
- putting sensitive-detail requests inside `trustedSupportSummary`, not only in
  `saferNextStep`.

The validator does not need to become a full natural-language classifier. It
only needs to reject common unsafe model-output patterns that would clearly
increase uncertainty or pressure.

## Proposed Test Scenarios

Add or extend tests in `lib/server/bedrock-response-validation.test.ts`.

### Sensitive Detail Request

Input:

```json
{
  "saferNextStep": "Ask them for the full bank account number and one-time code.",
  "why": "This helps confirm the payment.",
  "verificationSteps": ["Ask for their bank details."],
  "trustedSupportSummary": "I need to share a code to confirm this."
}
```

Expected:

```ts
{
  valid: false,
  reason: "safety_invariant_violation"
}
```

### Overclaiming Certainty

Input:

```json
{
  "saferNextStep": "This is definitely your daughter and the request is safe.",
  "why": "The video call proves it is real.",
  "verificationSteps": ["Send the money."],
  "trustedSupportSummary": "AskSafe confirmed this is genuine."
}
```

Expected:

```ts
{
  valid: false,
  reason: "safety_invariant_violation"
}
```

### Suspicious-Channel Verification

Input:

```json
{
  "saferNextStep": "Reply to the message and use the phone number they sent.",
  "why": "That will verify the request.",
  "verificationSteps": ["Use the contact details in the message."],
  "trustedSupportSummary": "I should call the number from the message."
}
```

Expected:

```ts
{
  valid: false,
  reason: "safety_invariant_violation"
}
```

### Safe Official-Channel Wording

Input:

```json
{
  "saferNextStep": "Pause before paying and contact the person using a number you already trust.",
  "why": "A money request should be checked through another channel before you act.",
  "verificationSteps": [
    "Do not use contact details from the message.",
    "Call the person using a saved number.",
    "Ask whether they really sent the request."
  ],
  "trustedSupportSummary": "I received a money request and want help checking it safely."
}
```

Expected:

```ts
{
  valid: true
}
```

## Implementation Boundary

The implementation should stay inside:

- `lib/server/bedrock-response-validation.ts`
- `lib/server/bedrock-response-validation.test.ts`
- optional docs update in `docs/architecture/bedrock-ai-orchestration-finops-design.md`

It should not modify:

- Terraform;
- AWS IAM policy;
- Vercel settings;
- Bedrock model IDs;
- frontend result layout;
- persistence table schemas.

## Acceptance Criteria

- Tests reject Bedrock output that asks for sensitive details.
- Tests reject Bedrock output that overclaims certainty about a person, message,
  or organisation being real or fake.
- Tests reject Bedrock output that tells the user to verify through suspicious
  contact details.
- Tests still accept calm official-channel wording.
- Existing Bedrock fallback tests continue to pass.
- TypeScript continues to pass.
- The AI response safety contract is documented clearly enough for product,
  engineering, and QA review.
